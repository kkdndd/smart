# 대교홀딩스 SMART 사업계획 관리 시스템

## 구성
- 프론트엔드: 정적 HTML/CSS(Tailwind CDN)/JS, 프레임워크 없음
- 백엔드/DB/인증/파일저장: Supabase (project ref: cbvjjocihktcbvfqsbyq, region: ap-northeast-2)
- 배포: Cloudflare Pages (정적 호스팅)

## 로컬에서 미리보기
이 폴더(web/)를 그대로 정적 서버로 띄우면 됩니다. 예:
```
npx serve .
```

## Cloudflare Pages 배포 방법
### 방법 A: Git 연동 (권장)
1. 이 web/ 폴더를 GitHub(또는 GitLab) 저장소로 push
2. Cloudflare 대시보드 → Workers & Pages → Create → Pages → Connect to Git
3. 빌드 설정: Build command 없음(정적 파일), Build output directory: `/` (web 폴더 자체가 루트)
4. 배포 후 `*.pages.dev` 주소가 발급되며, 이후 저장소에 push할 때마다 자동 재배포됩니다.

### 방법 B: 직접 업로드
1. Cloudflare 대시보드 → Workers & Pages → Create → Pages → Upload assets
2. web/ 폴더 전체를 업로드

도메인은 별도로 없으므로 우선 `*.pages.dev` 기본 주소를 사용하고, 추후 커스텀 도메인을 연결할 수 있습니다.

## 초기 계정 세팅 (최초 1회, 관리자 작업)
1. Supabase 대시보드 → Authentication → Users → Invite user 로 @daekyo.co.kr 이메일 초대
   (이 시스템은 auth.users insert 시 도메인이 @daekyo.co.kr 가 아니면 자동으로 거부되도록 DB 트리거가 설정되어 있습니다)
2. 초대받은 사용자는 이메일의 링크로 비밀번호를 설정 후 로그인
3. **최초 관리자 부트스트랩**: 처음에는 아무도 지주사 권한(holdco_staff)이 없으므로, 최소 1명은
   Supabase SQL Editor에서 아래 SQL을 직접 실행해 지주사 관리자로 승격해야 합니다.
   ```sql
   update profiles set role = 'holdco_staff', company_id = null
   where email = '최초관리자@daekyo.co.kr';
   ```
4. 이후부터는 이 관리자가 `admin.html` (계정 관리) 화면에서 다른 사용자의 소속 계열사/역할/담당 사업부를 지정할 수 있습니다.

## 핵심지표(KPI) 입력 규칙
- 목표당 지표는 **최소 1개**, 지표명은 필수이며 같은 목표 안에서 중복될 수 없습니다(공백·대소문자 무시 비교).
- 정량형(증가형·감소형)은 목표값 방식을 하나 이상 골라야 하고, **고른 방식에 실제 값이 들어가 있어야** 저장됩니다.
  - 연간 목표값 0은 달성률 계산이 불가능하므로 막습니다.
  - 감소형은 기준값이 필수입니다(달성률 = (기준값 − 실적) ÷ (기준값 − 목표값)).
- 정성형(마일스톤·진척도)은 기준값·목표값·단위를 저장하지 않습니다(화면에서 감춘 값이 남아 저장되던 문제 방지).
- **저장 순서**: 모든 검증을 통과한 뒤에야 DB에 씁니다. 예전에는 지표를 먼저 삭제하고 검증해서, 검증에 걸리면 기존 지표가 사라졌습니다.
- **지표 id 유지**: 수정 저장 시 기존 지표는 `update`로 갱신하고, 화면에서 제거된 지표만 삭제합니다.
  지표를 삭제하면 `progress_entries`가 CASCADE로 함께 지워지므로, 실적이 있는 지표를 지울 때는 화면에서 경고합니다.
- 신규 작성 중 오류가 나도 목표가 중복 생성되지 않도록, 목표 생성 직후 수정 모드로 전환합니다(URL에 `?id=` 반영).

## 목표 관리번호(seq_no) 채번 규칙
- 번호는 **연도 + 계열사 + 사업부** 그룹 안에서 1번부터 매겨집니다. → "2026년 강원심층수 영업 1번 목표"
- 사업부를 지정하지 않은 전사 공통 목표는 `business_unit_id IS NULL` 끼리 하나의 그룹으로 묶여 따로 채번됩니다.
- 신규 등록 시 `trg_assign_goal_seq_no` 트리거가 자동으로 다음 번호를 부여합니다(화면에서 입력하지 않음).
- 목표의 사업부(또는 연도·계열사)를 바꾸면 **옮겨간 그룹 기준으로 번호가 다시 부여**됩니다. 내용만 수정하면 번호는 그대로입니다.
- `goals_seq_no_per_group_key` 유니크 인덱스(`NULLS NOT DISTINCT`)가 같은 그룹 내 번호 중복을 DB에서 차단합니다.
- 목표를 삭제하면 그 번호는 비어 있는 채로 남습니다(기존 번호를 밀어서 바꾸지 않음 — 이미 공유된 번호가 달라지는 것을 막기 위함).
- 목록 화면은 사업부로 묶은 뒤 번호 순으로 정렬합니다(`common.js`의 `sortGoalsByBusinessUnit`).

## 로그인 세션 정책
- 로그인 토큰은 **sessionStorage**에 저장됩니다(`js/common.js`의 `AUTH_STORAGE`).
  브라우저나 탭을 닫으면 토큰이 사라지므로, 다시 접속하면 로그인 화면부터 시작합니다.
- sessionStorage는 탭 단위로 유지되므로 같은 탭 안에서 페이지를 이동하는 것(이 앱은 전체 새로고침 방식)에는 영향이 없습니다.
- 방식 전환 이전에 localStorage에 남아 있던 `sb-*-auth-token` 키는 페이지를 열 때 자동으로 정리됩니다.
  그래서 전환 직후 한 번은 기존 사용자 전원이 다시 로그인해야 합니다.
- 한계: 크롬의 "중단한 부분부터 계속하기"(세션 복원)가 켜져 있으면 탭과 함께 sessionStorage까지 복원될 수 있어 100% 보장은 아닙니다.
  또한 링크를 새 탭으로 열면 그 탭에서는 다시 로그인해야 합니다.
- 더 엄격하게 막으려면 ① 앱 레벨 유휴 타임아웃(마지막 활동 후 N분 경과 시 자동 로그아웃) 추가,
  ② Supabase Pro 플랜의 Time-box / Inactivity timeout 사용을 검토할 수 있습니다.

## 비밀번호 관리
- **본인 변경**: 로그인 후 좌측 사이드바 하단 [비밀번호 변경] → `password.html`.
  현재 비밀번호로 본인 확인 후 새 비밀번호를 설정합니다. (8자 이상 + 영문·숫자·특수문자 중 2종류 이상)
- **최초 로그인 강제 변경**: 계정 생성 시 `profiles.must_change_password = true`가 기본값이라,
  관리자가 발급한 초기 비밀번호로 처음 로그인하면 `password.html`로 자동 이동하며
  비밀번호를 바꾸기 전에는 다른 화면으로 이동할 수 없습니다(사이드바·취소 버튼도 숨김).
- 이메일 링크로 직접 비밀번호를 설정한 경우(`reset-password.html`)에는 중복으로 요구하지 않고 자동 해제됩니다.
- 관리자가 비밀번호를 재발급해준 경우, `admin.html`의 [변경 요구] 버튼으로 강제 변경 절차를 다시 걸 수 있습니다.
- 기존에 이미 사용 중이던 계정은 이 기능 도입 시점에 변경 요구 대상에서 제외되었습니다.

## 권한 구조 (지주사 - 계열사 - 사업부 3단계)

| 역할 | 조회 범위 | 주요 권한 |
| --- | --- | --- |
| 사업부 담당자 (`bu_staff`) | 배정된 사업부만 | 목표 작성 → 계열사 검토 제출, 실적 입력 |
| 계열사 담당자 (`company_staff`) | 자기 회사 전체 사업부 | 사업부 제출 목표 검토(합의/수정요청), 전사 목표 직접 작성, 사업부 등록·병합 |
| 지주사 담당자 (`holdco_staff`) | 전 계열사 | 최종 합의/반려, 계정·권한 관리(유일), 계열사·사업부 관리 |
| 지주사 경영진 (`holdco_exec`) | 전 계열사 | 조회 전용 |

- 계정·권한 배정(역할 지정, 사업부 배정)은 **지주사 담당자만** 가능합니다. (`profile_business_units` 테이블 RLS로 강제)
- 사업부 담당자는 겸직이 가능하며, 여러 사업부를 배정받을 수 있습니다.

### 목표 결재 흐름
```
사업부 담당자 작성 → [임시저장]
      ↓ 계열사 검토 제출
[계열사 검토중] ── 수정요청 → [수정요청] (사업부가 수정 후 재제출)
      ↓ 계열사 합의
[지주사 검토중] ── 수정요청/반려 → [수정요청] / [임시저장]
      ↓ 지주사 최종 합의
[합의완료]
```
- 계열사 담당자가 직접 작성한 목표는 제출 시 곧바로 `지주사 검토중` 상태가 됩니다.
- 월별/분기별 **진행실적 입력은 별도 결재 없이** 입력 즉시 반영됩니다.

### 계열사·사업부 마스터 관리 (숨김 / 삭제)
- `companies.html`(계열사 관리, 지주사 담당자 전용), `business-units.html`(사업부 관리, 계열사·지주사 담당자)
- **표시 기간**(`active_from_year` / `active_to_year`): 연도별로 대상 조직이 달라지는 경우에 사용합니다.
  - 종료 연도를 `2025`로 지정하면 → 2026년 이후 대시보드·목표 목록·필터에서 제외되고, **2025년 이하를 조회하면 과거 실적이 그대로 보입니다.**
  - 시작 연도를 `2027`로 지정하면 → 2027년부터 노출됩니다. (신설 계열사·사업부를 미리 등록할 때)
  - 판정 규칙은 `common.js`의 `isVisibleInYear()`(조회 노출) / `isSelectableInYear()`(신규 선택 가능) 한 곳에 모여 있습니다.
- **전체 숨김**(`is_active = false`, 표시 기간 미지정): 연도와 무관하게 모든 조회 화면에서 제외됩니다.
  과거 연도 대시보드에서도 사라지므로, 지난 실적을 계속 보려면 전체 숨김 대신 표시 종료 연도를 쓰세요.
  이미 입력된 목표·실적·첨부파일은 전혀 건드리지 않으며, 과거 데이터 화면에는 그대로 표시됩니다.
  숨긴 사업부로 등록된 기존 목표를 수정할 때는 해당 사업부가 `(숨김)` 표기와 함께 선택 목록에 계속 남습니다.
- **삭제**: 연결된 데이터(목표·사업부·계정)가 하나도 없을 때만 가능합니다.
  데이터가 있는 계열사·사업부는 삭제 대신 숨김 처리하도록 막아, 과거 실적이 유실되지 않게 합니다.

### 사업부 중복 등록 방지
- `business_units`에 공백·대소문자를 무시한 정규화 이름(`name_norm`) 기준 회사별 유니크 인덱스가 걸려 있어,
  "온채널"과 "온 채널"처럼 표기만 다른 중복 등록이 DB 레벨에서 차단됩니다.
- 이미 생긴 중복은 `business-units.html`(사업부 관리)의 **병합** 기능으로 정리할 수 있습니다.
  병합 시 해당 사업부의 목표와 담당자 배정이 대상 사업부로 모두 이관됩니다. (`merge_business_unit` RPC)
